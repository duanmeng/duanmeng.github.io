Velox Primer 1,2,3

duanmeng
2025-12-30
technology
QueryExecution, Velox

阅读 Velox，先把“一次查询”拆成不同尺度：集群中的 stage/task、一个 Task 内的 pipeline/driver、一个 Driver 内的 operator，以及算子之间流动的 RowVector。名字相近，但它们的生命周期、并行方式和数据所有权不同。

本文于 2026-09-19 对照 Velox 1d1b76567870 重写，沿用原来 Primer 1、2、3 的学习顺序：执行模型、初始化、数据流。示例是结构示意，不依赖某个宿主恰好生成完全相同的计划。

1. 第一层：分布式计划与 Velox Task

宿主把分布式查询切成 plan fragments，再把同一 fragment 的多个 task 调度到不同 worker。Velox Task 执行其中一个 fragment；Stage 的集群级调度和失败重试通常属于宿主，不由单个 Velox Task 管理。

概念 表示什么 不应等同于
Query 一次逻辑查询 一个 Velox Task
Stage 宿主执行同一 fragment 的一组任务 一个线程
Task 一个 fragment 的执行实例 一个 split
Split 发给某个 source plan node 的工作单元 一个固定大小 RowVector
RowVector 算子间流动的一批数据 文件或远程 task

同一个 Task 可以消费很多 split。文件 split 通常描述路径、范围等 connector 信息，远程 split 则标识交换来源；source operator 根据 split 取数据。一份文件 split 可以产出很多 batch。

2. Task、Split 和“没有数据”的三种含义

Task 按 source planNodeId 和 split group 组织 split store。TableScan 等 source operator 通过 getSplitOrFuture 请求下一份工作。

  • 队列有 split：取走并开始处理。
  • 队列空、未来仍可能来 split：返回等待 future，Driver 暂时让出执行线程。
  • 队列空、已经收到结束信号：该输入才真正结束。

noMoreSplits(planNodeId) 表示宿主不会再给这个 source 添加工作；noMoreInput() 是算子之间的结束通知。它们不是同一个接口，也不意味着收到信号那一刻输出已经全部消费。grouped execution 还有 group 级结束信号。参见 split 结束处理。

split 到达后唤醒等待者，等待者继续获取工作。未来通知和实际队列状态配合形成协议；空队列本身不是完成条件。

3. Pipeline、Driver 和 Operator

一条 pipeline 是能够顺序推进的一组算子；一个 Driver 是它的运行实例。多个 Driver 可以执行同样的 pipeline，各有自己的 Operator 状态；它们通过 Task 持有的共享对象交流。

LocalPlanner 从计划树产生 DriverFactory，createDriver 再建立 Operator 链。一个 PlanNode 不一定只对应一个 Operator：HashJoin 的 probe 在一条 pipeline，build 在另一条 pipeline，两边通过 HashJoinBridge 关联。

Driver 数也不等于线程数。Driver 在 executor 上运行，阻塞时保存继续执行所需状态和 future；future 就绪后重新入队，后续可能由另一个线程运行。同一个 Driver 的算子链保持串行推进。

统一接口，不同状态

needsInput() 表示当前能否接受输入；addInput() 接管一批输入；getOutput() 尝试产生输出；isBlocked() 提供等待原因和 future；isFinished() 表示不会再有输出。

getOutput() == nullptr 可能是暂时没有输出，也可能是 sink 本来就不通过这个接口输出。Driver 必须结合这些方法推进，不能写成“所有算子循环 getOutput，返回空即退出”。准确执行循环见 Task & Driver。

4. 第二层：初始化与资源注入

一个并行 Task 的准备过程可以这样阅读：

宿主准备 PlanFragment、QueryCtx、executor、connector、输出接口
    → Task::create
    → LocalPlanner 生成 DriverFactory
    → Task 创建共享状态、内存层次及 Driver 实例
    → Operator 初始化
    → Task::start 调度执行
    → split 可以继续逐批到达

这是依赖关系示意，并不表示所有对象都在 create 调用内立即构造完毕。不同执行模式和 grouped execution 会改变具体时机。代码入口是 Task::create 和 LocalPlanner::plan。

QueryCtx 提供 query 配置、pool、executor、缓存等。可以让 QueryCtx::Builder 默认创建 root，也可注入宿主创建的 root。executor 的生命周期要长于使用它的 Task，不能在创建 QueryCtx 的局部函数结束时就销毁线程池。

Task::start(maxDrivers, ...) 中的 maxDrivers 是约束，实际每条 pipeline 的 Driver 数还受 plan node、consumer、查询配置与执行模式限制。MergeJoin 等路径可能要求单线程；不能简单估成“plan node 数 × maxDrivers”。参见 Driver 数量约束。

5. 用一次分组聚合串起流水线

考虑以下查询的某个 worker 局部执行部分：

SELECT k, sum(v)
FROM t
WHERE v > 0
GROUP BY k;

一种可行的本地结构是扫描/过滤/partial aggregation 后按 k 重分区，再由下游合并聚合。分布式计划还可能在 stage 边界添加 PartitionedOutput 和 Exchange；这里先只看 Task 内：

Partial aggregation 不是把最终结果直接打印出来，而是产生可继续合并的状态。对于 sum，状态相对简单；对于 avg，需要保留足够信息以合并总和与数量，不能把各分区平均值再做不加权平均。

聚合的 partial/intermediate/final/single step 决定输入和输出的语义。物理计划必须保证 final 聚合看到同一个 key 的全部相关中间态。Velox 执行的是宿主给定的计划，不能在阅读一个 HashAggregation 时假定全局分区条件自动成立。

6. 第三层：LocalPartition 与 LocalExchange

LocalPartition 是 producer pipeline 末端的 sink；LocalExchange 是 consumer pipeline 开头的 source。共享的 LocalExchangeQueue 保存待消费 batch，LocalExchangeMemoryManager 管理缓冲占用与背压。

输入按分区函数拆分后，常用 dictionary 包装引用原始列，从而避免为每个分区复制全部值。wrapChildren 还会处理已有包装、lazy/constant 等情况。这里的“零拷贝”主要指复用底层值，索引 buffer、包装对象和某些加载仍有成本。

enqueue 会先把数据放入队列并计入占用；超过阈值时返回等待 consumer 的 future。因此内存阈值是背压门槛，不是一个 batch 都不能越过的硬上界。consumer 取走数据后释放记账并唤醒 producer；consumer 无数据时则等待 producer。

结束还需要计数：不再增加 producer、已有 producer 都报告 noMoreData、队列排空，才能宣布消费结束。单个 producer 完成，不代表整个 exchange 完成。

7. 字典、阻塞算子与 Pipeline 边界

Dictionary 的逻辑是 output[i] = base[indices[i]]。多个输出可以共享 base；这降低搬运成本，也延长 base buffer 的存活时间。若下游只保留少量行，却间接引用一个很大的输入批次，retained memory 可能比逻辑输出大小大得多。

Local exchange 是显式的数据传递边界，HashJoin 则是构建状态发布的边界：

  • HashBuild 消费 build 数据，准备共享 hash table。
  • HashProbe 等待 bridge 提供表，然后 probe。
  • 启用 spill 时，两侧还可能经过多轮 build/probe/restore。

HashAggregation、OrderBy 等算子内部也会缓存状态，但“算子需要缓冲”不等于 LocalPlanner 一定为它切出一条独立 pipeline。是否拆分以计划节点的边界规则为准。HashAggregation 的某些 partial 路径可以提前输出；OrderBy 的常规完整排序则需要知道输入结束后才能按全局顺序输出。

8. 本地交换与跨 Task 交换

跨 Task 的常规流式交换大致是：

上游 PartitionedOutput
    → 序列化页 / OutputBuffer
    → 宿主实现的 ExchangeSource 传输
    → 下游 InMemoryExchangeClient / ExchangeQueue
    → Exchange 反序列化成 RowVector

这条路径与 LocalPartition/LocalExchange 不是同一个队列。跨 Task 还涉及来源发现、传输 token、acknowledgement、输出缓冲清理与网络错误。当前 Velox 的 ExchangeSource 是抽象扩展点，Presto 的 HTTP 协议位于 Presto 仓库。

并非所有交换都走这个路径：materialized/file exchange 和其他 transport 可以有不同实现。完整宿主链路见 Query in Presto Worker。

9. 读代码时先问哪几个问题

遇到一个算子，先找输入从哪里来、输出交给谁、哪些状态属于当前 Driver、哪些状态由 Task 共享；再找等待条件和唤醒者，最后找结束、取消和 reclaim 路径。

现象 优先检查
source 一直等 split planNodeId、group、split 添加和 noMore 信号
producer 一直等待 下游是否消费、队列占用、future 是否被通知
join 不输出 build 是否完成、bridge 是否发布、probe 状态
Driver 很多但 CPU 不高 split/IO/背压等待、pipeline 单线程约束
输出很少但内存很大 dictionary 保留、聚合/join 状态、reserved 与 used

本文核对了当前接口与实现，未运行完整执行测试。进一步阅读：Task、Driver、LocalPlanner、LocalExchangeQueue，再进入 HashJoin 与 Spiller。
