Velox Parquet SelectiveReader：过滤下推、延迟物化与 I/O 调度

duanmeng
2026-09-26
technology
IO, Parquet, PredicatePushdown, SelectiveReader, Velox

Velox 的 Parquet SelectiveReader 是 Hive connector 把 Parquet 文件读成 Velox 向量的一条执行路径。上层交给它文件 split、需要的列和过滤条件；它组织列 reader，先筛选行，再为需要的行生成列值，最后交回 RowVector。这里的“selective”有两个含义：列可以少读，列中的值也可以按行集合选择性解码。它同时连接查询表达式、Parquet 编码和底层 I/O，不能只从某一个 ColumnReader 类来理解。

这条路径的入口是 HiveDataSource。当前实现把公共文件扫描流程放在 FileDataSource 和 FileSplitReader；Hive 子类负责分区值、合成列、bucket conversion 等语义。往下，ParquetRowReader 决定读哪个 RowGroup、推进多少行，StructColumnReader 协调各列的过滤与输出，叶子 reader 和 PageReader 完成编码解码，BufferedInput 则决定何时取得文件字节。

下面先跟踪一条查询从 Hive 到返回 batch 的完整过程，再展开嵌套数据、跨页状态、预取与异常。理解这条路径需要始终区分三种东西：查询所需的值、reader 当前选择的行号、存储实际读取的字节。返回一行不等于只读一行的字节；一个 LazyVector 也不意味着对应的压缩数据还没有进入内存。

代码基准：2026-09-29 获取的 Velox origin/main，432a2e73b2c1。本文分析普通 CPU Hive → Parquet 路径。源码摘录固定到此版本；SQL 和行号算例用于解释接口，未作为完整 Velox 程序编译。原分享的例子、行业背景和 PageReader 完整函数保留在对应章节与附录。

1. 从 HiveDataSource 看整条读取链

TableScan 不直接打开 Parquet 文件。它先从 Task 取得 connector split，通过 HiveConnector::createDataSource() 创建 HiveDataSource；后者的构造函数委托给 FileDataSource。第一次创建时编译查询需要的读取方案，之后每个 split 创建自己的 split reader。DataSource 是一次扫描的上下文，split reader 是当前文件范围的上下文，两者生命周期不同。

图中的主调用链是一条同步 C++ 调用栈；后台 split preload 和数据预取是另外的执行活动。Driver 自身可在线程池上被调度，遇到算子级 future 时可以让出线程，但不能据此推断这条栈中的每个文件读取都是异步接口。TableScan 的 split preload与下文 DirectInputStream 的等待方式需要分别分析。

2. 一条查询怎样变成读取方案

用 nation 的前 11 行作为数据，增加一个值来自 split 的分区列 ds。假设文件中的 nationkey 与 regionkey 是 BIGINT，name/comment 是 VARCHAR；ds 为 VARCHAR 分区值。主例的 WHERE 同时包含分区条件、可直接用于 reader 的整数范围和需要表达式求值的两列加法。

贯穿全文的查询示例

SELECT name AS country, comment, ds
FROM nation
WHERE ds = '2026-09-01'
  AND nationkey BETWEEN 0 AND 3
  AND nationkey + regionkey >= 4;

2.1 TableHandle 与 assignments 分别描述什么

HiveTableHandle 继承文件表句柄的公共语义，保存表的数据列、subfieldFilters、remainingFilter 等；ColumnHandle 描述某个字段的实际名字、类型和列种类。TableScan 的 outputType 使用执行计划中的输出名字，assignments 把这些名字映射到 column handle。因此 country 是上层输出字段，name 才是文件中要寻找的字段，不能把二者直接拿来按名字匹配。

名称 / 对象主例中的内容使用位置

还要区分一个容易混淆的参数：RowReaderOptions::requestedType 并非直接等于 readerOutputType_。FileSplitReader::getAdaptedRowType 从 baseReader 的文件字段名出发，调用 HiveSplitReader::adaptColumns 调整字段目标类型，再把这个 row type 传给 createRowReader。readerOutputType_ 描述 connector 需要的内部结果列；adapted row type 则给列 reader 提供文件字段的目标类型视图。这样 ScanSpec 中非投影的 filter-only 字段也能找到其类型。

这三份 schema 都通过 Velox 的 Type / RowType 表达逻辑类型；ParquetTypeWithId 额外记录物理存储和层级信息。它们不是三套 C++ struct，也不是把一列从“逻辑类型”强转成“物理类型”。INT32/INT64 等文件存储形式、DATE/DECIMAL 等逻辑含义，以及 reader 的 C++ 解码宽度，在更下层才关联起来。

2.2 只过滤的列，什么时候也必须成为 reader 的输出列

对于 SELECT name WHERE nationkey BETWEEN 0 AND 3，nationkey 只需产生通过行号，ScanSpec 可以保留它作为 filter-only child，不需要把其值放进最终 RowVector。但主例的加法还需要 nationkey 的值，FileDataSource 会将其补入 readerOutputType，让 reader 在过滤时保留这些值。regionkey 同样被补入。它们对 SQL 是隐藏列，对 connector 内部 ExprSet 却是输入列。

readerProducedType_ 是公共基类为 extraction pushdown 等变换预留的结果 schema。当前 ParquetColumnReader::build 明确检查 extractionType 必须为 kNone，因此不能把公共代码中存在的 transform 分支写成这条 Parquet 主线必定支持的能力。

3. 一次扫描怎样从 11 行得到 1 行结果

沿上一节的 SQL 走完一批数据，再展开 ScanSpec、RowGroup、ColumnReader 与 I/O。这里的 remaining filter 是 nationkey + regionkey >= 4；后面的双 reader-filter nation 示例则使用 regionkey=0，它们刻意展示两种过滤放置方式，不能合并成同一个条件。

4. ScanSpec：把查询要求编译到列树上

ScanSpec 是连接 Hive 查询语义与 DWIO 列 reader 的共享对象。它既不是 Parquet footer，也不是单纯的过滤表达式树。每个节点对应字段或 subfield，记录过滤器、是否产出值、结果 channel、常量值、读取下标，以及过滤计时和选择率。创建 reader 后，它还承载跨 batch 的自适应状态。

4.1 先拆能下推的条件，再编译 remaining ExprSet

FileDataSource 首先复制 table handle 的 subfieldFilters，再调用 extractFiltersFromRemainingFilter。这个函数尝试把叶子表达式转换为 SubfieldFilter；同一字段已有 filter 时合并。AND 中可提取的部分可以独立下推；OR 则必须满足可表示性约束，例如各分支都能完整转成同一 subfield 的 filter，再合成 OR filter，不能把 a=1 OR b=2 拆成两列同时成立。NOT 通过 negated 状态递归处理；识别出的采样表达式可以转成 sampleRate/RandomSkip。

主例中 nationkey 的区间可用 BigintRange 表达，nationkey+regionkey≥4 仍是 ExprSet。关键边界是 reader 的 filter 抽象能否表达该条件，不是“单列一律下推、多列一律不下推”。提取代码见 HiveConnectorUtil.cpp:761。

4.2 makeScanSpec 的两轮列处理

makeScanSpec 先处理 readerOutputType 中要产出的字段，为它们设置 channel，并递归添加全部或必要的 subfields。随后处理只在 subfieldFilters 出现、没有被产出的字段：从 table 的 dataColumns 找到类型，在 ScanSpec 中添加非投影节点。最后把各个 filter 安装到准确的 subfield 节点。这就是“filter-only 列没有输出 channel，也仍有 ColumnReader”的来源。

6. Parquet 布局与 footer：查询要求落到哪些字节

6.1 RowGroup、ColumnChunk 与 footer

Parquet 可以看作文件级的 PAX 风格组织：先按行水平切成 RowGroup，再把每个 RowGroup 内各叶子列的数据分别放进 ColumnChunk。一个包含 A、B、C 三个叶子列和两个 RowGroup 的文件，共有六个 ColumnChunk。每个 chunk 有一个或多个 page；字典编码时可能先有 dictionary page。不同列的 page 大小和行边界不要求对齐。

footer 保存 schema、RowGroup 行数、ColumnChunk 位置与长度、codec、encoding、统计等元数据。reader 可以在解码数据前用这些信息选择范围。简单文件还在首尾使用 PAR1 标识，尾部记录 footer 长度；图中聚焦 chunk 与 footer，并未按真实字节比例画所有格式字段。

6.2 Data Page V1 与 V2 的压缩边界

逻辑布局示意；不是 C++ 数据结构

[ PageHeader: Thrift, variable length ]
[ repetition levels, if present ]
[ definition levels, if present ]
[ encoded values ]

V1 在启用 codec 时，对页体中的 levels 与 encoded values 整体压缩。V2 在 header 中给出 repetition_levels_byte_length 和 definition_levels_byte_length，levels 本身不压缩；values 是否压缩由 is_compressed 决定。当前 prepareDataPageV2() 把缺省 is_compressed 按 true 处理，并验证 levelsSize 不超过 compressed/uncompressed page size。分析读取成本时，需要按 page version 分开计算 levels 与 values 的处理。

“page 内只需要两行”通常无法让通用压缩器只解压两行对应的字节。reader 需要先获得对应压缩块，再在 encoded values 中跳过不需要的项。不过，value decode、结果写入以及后面列的读取仍可以少做。这正是 page 裁剪与 row 裁剪应该分别讨论的原因。

footer 解码后的 Thrift 对象也有内存成本。ReaderBase 按阈值估算并 reportExternalAllocation；RowGroup 过滤释放不读组的 ColumnChunk metadata 时相应 releaseThriftBytes，析构释放剩余报告值。原始压缩文件大小、解码值 buffer 大小和 footer 内存大小，必须分开看。

7. 从 schema 到 reader tree：类型、列下标与所有权

文件 schema 决定可读的物理 leaf，ScanSpec 决定本次扫描需要哪些字段，两者共同决定 reader tree。ParquetColumnReader::build 接收 requestedType、fileType 和 ScanSpec：按照文件 TypeKind 选择具体 reader，再由 reader 处理目标类型。比如整数列可在 getValues 时按 requested type 输出，DECIMAL 还可能有 scale 扩大；这不是将原始 Parquet 字节直接解释为任意 C++ 目标类型。

文件 schema、查询 requested type、运行时 Vector 和 reader tree 有关联，但不是同一个对象。requested type 使用 Velox Type 描述逻辑语义；ParquetTypeWithId 还保留物理 schema、列号、父子路径和 level 信息；Vector 表示输出数据和编码；ColumnReader 维护解码与扫描状态。

以 ROW(c0 BIGINT, c1 MAP(VARCHAR, DOUBLE)) 为例，顶层 RowVector 直接有两个 child：c0 的整数 vector 和 c1 的 MapVector。MapVector 自己有 offsets、sizes 和 nulls，再持有 key/value vectors。因此总共三条 leaf values 流，但绝不能说整棵树只有三个 Vector。reader 一侧对应 root StructColumnReader、IntegerColumnReader、MapColumnReader，map 下再有 StringColumnReader 与 FloatingPointColumnReader<double,double>。

工厂 ParquetColumnReader::build 根据 fileType 的 Velox kind 选择具体 reader，再结合 requestedType 处理读取结果类型。整数走 IntegerColumnReader；REAL 可按 requested type 输出 float 或 double；ARRAY/MAP/ROW 走相应复杂 reader；timestamp 还要区分文件 INT64/INT96。C++ 值类型由 decoder/visitor 模板承接，和顶层 logical Type 的职责不同。

StructColumnReader 构造时使用 ScanSpec::stableChildren() 建立 children_，为每个真实 reader 设置 subscript。之后 ScanSpec::children() 可以因过滤重排而改变顺序；reader 在 children_ 中的位置和输出 channel 都不能跟着随意变。channel 指输出列位置，subscript 指实际 reader 位置，遍历顺序指当前读取优先级，必须分清。

复杂节点并不总有自己的物理值 stream。嵌套 struct 的 nullability 需要从 descendant leaf 的 RL/DL 推导；本版本还有 synthetic rep/def source：当逻辑投影 child 不足以提供结构信息时，选择一个物理叶子专门读取 levels。源码按完整 metadata、读取字节、解压字节、numValues 等成本选择候选。因此 reader tree 与“查询投影的物理叶子”也不是无条件一一对应。

构建 StructColumnReader 时按 stableChildren 创建子 reader，并把 children_ 下标写进每个 childSpec.subscript。运行时 ScanSpec.children() 可以为了过滤成本重排，但 subscript 仍指向同一 reader，channel 仍指向同一结果列。需要分别记住“调用顺序”“reader 地址”“输出位置”这三个坐标。

8. RowGroup 选择、预取窗口与组内游标

RowReader 构造完 reader tree 后，立即执行 filterRowGroups；只要有有效组，就调用 advanceToNextRowGroup。也就是说，第一组的 I/O 规划通常发生在 addSplit/prepareSplit 中，不必等第一次 next。若 split 已在后台 preload，这些工作也会提前发生。

当前过滤入口是 ParquetRowReader::Impl::filterRowGroups()。它先用 split 的 [offset,limit) 和 RowGroup 文件起始 offset 排除不属于此 split 的组，再排除空组；随后调用 columnReader_->filterRowGroups 评估列统计，并把 MetadataFilter 的组合结果纳入排除位图。RowReader 决定有效组列表，ReaderBase 随后负责输入调度，二者职责不同。

split 是文件字节范围；RowGroup 是否由它处理根据文件位置归属判断，不是随意把一个 RowGroup 在行中间切开。跳过的组不进入 rowGroupIds_。统计只允许排除“不可能通过”的组；缺失或不足以判断的统计必须保留候选。

主例在 reader 中只有 nationkey 范围 filter；加法留给 FileDataSource。reader 输出四行后，ExprSet 按这四个逻辑位置访问 regionkey，得到 [0,2,3,4] 的和。仅位置 3 通过，于是 name/comment 外面可以包一层 indices=[3] 的 dictionary；下游第一次访问时才请求这个位置。下面把这件事推广到稀疏 reader 输出。

13.1 单列 filter 和表达式层 filter 的边界

SubfieldFilter 是 reader 能识别的字段或 subfield 条件，例如整数范围、字符串范围、null 检查等。复杂函数、不能提取成这些条件的单列表达式，或 c0+c1>10 这样的多列计算，交给 remaining ExprSet。并不是“单列一定下推，多列一定不下推”：FileDataSource 先调用 extractFiltersFromRemainingFilter，把能提取的部分放回 filters_，其余才编译为表达式。

payload 是不参与当前 predicate 的投影列。LazyVector 是带逻辑长度和 VectorLoader 的延迟表示，不保证文件 I/O 尚未发生：可能已经 prefetch 了压缩数据，只是尚未 decode 成 values。区分“延迟 stream I/O”和“延迟 value materialization”十分关键。

13.2 Parquet 的真实 lazy 条件，不由 remainingFilterColumns 直接决定

FileDataSource 确实收集 remainingFilterColumns_ 并传到 RowReaderOptions，但在本文版本中，直接使用 remainingFilterColumns() 排除 lazy I/O 列的是 SelectiveNimbleRowReader::computeLazyIoColumns()。它控制 Nimble 的 stream I/O 延迟集合，也不等于所有格式的统一 eager-vector 开关。Parquet 的 StructColumnReader 没有消费这个集合；其 lazy 条件是read/getValues 一节的源码中的 top-level/projectOut/filter/generateLazyChildren。

因此，Parquet reader 返回时，remaining filter 引用的列仍可能是 LazyVector。ExprSet 求值会加载实际需要的字段；对多次引用或 shouldEagerlyMaterialize 判断出的字段，FileDataSource 在 evaluateRemainingFilter 前显式 ensureLoadedRows，避免同一个 lazy child 在多个表达式分支中被不一致地局部加载。过滤需要但 SQL 不投影的字段会补进 readerOutputType，求值后再去掉。

13.4 lazy 的生命周期约束

ColumnLoader 保存父 reader、field reader、创建版本和本批偏移。实际加载首先校验 version==structReader->numReads()，失败信息是 “Loading LazyVector after the enclosing reader has moved”。保留一个旧 batch 的未加载 LazyVector，并让 reader 继续 next，不能被视为无限期可用的快照。buffer 共享和 reader 游标生命周期是两个不同问题。

15. PageReader：跨页坐标、字典转换与 null bitmap

到 PageReader 时，输入不是 SQL 表达式，而是 visitor 指定的一组目标位置，以及本 ColumnChunk 的 stream 和编码状态。一次 visitor 可能跨多个 page，page 内也可能包含未选择的位置。PageReader 要同时维持三个一致性条件：decoder 在正确位置、输出值连续排列、输出 nulls 与 outputRows 指向同一批结果。

15.1 RowSet 不是一个固定的文件绝对坐标

PageReader 中 visitorRows 是当前 visit 的相对行号，visitBase_ 由 startVisit 从 firstUnvisited_ 取得。对普通标量列，可以把两者之和理解为当前 ColumnChunk 对应的行位置；重复嵌套列的 leaf level/value 数不等于顶层 RowVector 行数，必须先经结构层转换。原附录把所有 visitorRows 直接叫“全局绝对行号”，会混淆层级。

rowsForPage 首先判断 visitor 是否已消费完；然后计算下一目标 rowZero。如果它超出当前 page，seekToPage 逐步解析 PageHeader 并移动流。遇到 numRowsInPage_==0 表示 chunk 末尾，函数返回 false。已知 page 行范围且目标在后面时，可 skip 该页数据；重复列可能先需要读 levels 才能知道边界，跳过不是无条件的。

15.2 一个具体的跨页坐标算例

设 visitBase=1000，visitorRows=[5,8,210,215]。Page A 覆盖 [1000,1200)，Page B 覆盖 [1200,1400)。page 切片把前两项交给 A，后两项交给 B。到了 B，pageOffset=1200−1000=200，rowNumberBias=210，先 skip(10)，让 decoder 位于绝对行 1210，再用 [0,5] 表示两个目标。filter 产生的输出行号加回 210 后，才恢复成本 batch 的 [210,215]。

还有一个完全不同的 numValuesBias：它表示之前 page 已经向 values buffer 写入了多少项，用来定位当前 page 结果的追加位置。输入行号的 bias 与输出 buffer 的 bias 不能互换。最后 firstUnvisited 更新为最后一个目标绝对位置加一，即本例 1216。

15.3 dictionary/direct 切换与 filter cache

同一 ColumnChunk 的 data pages 可以先 dictionary 后 plain。进入 dictionary page 时，scanState 指向当前字典，并在有 filter 时建立 filter cache。切到 direct page 前，如果先前积累的结果还是 dictionary ids，就要 dedictionarize。代码临时挂上已累计的 null bitmap，避免把 null 位置的未定义字典索引当作有效值读取；转换完成后清空 dictionary state，再准备新页 nulls。

15.4 多页 null bitmap 不能按输入长度盲目拼接

readWithVisitor 每页先记录 numValuesBeforePage，设置 visitor 的 rows 和 output bias，再 callDecoder。跨页时，BitConcatenation 按实际产出的值数拼接 nulls。没有 null 的页追加 ones（Velox 位图中 1 表示非空）；returnReaderNulls 的快路径直接取 reader 的输入 nulls；普通过滤/compact 路径取 mutableNulls，起点还要看 nullsFromFastPath 是否从零写入。

如果前一批输出仍共享 multiPageNulls_，代码先放弃复用旧 buffer，避免修改已交付的数据。delta binary packed decoder 耗尽时还校验内部指针到达页尾。最后把拼接结果 setNulls 回 reader，并用 rowNumberBias 修正通过行号。完整的两个函数保留在附录，正文逐一解释其状态。

PageHeader 中的长度来自文件，不能在边界检查前直接相加或传给解压器。当前 V1/V2 路径对负长度、level 区域越界、解压大小不匹配等设置检查；ParquetPageReaderTest 覆盖 corruptDefineLengthV1、corruptLevelLengthsV2、snappyUncompressedSizeMismatch 等情形。这些保护与 SIMD 尾部 padding 一样，都属于高性能 reader 的正确性前提。

16. BufferedInput：列的读取需求怎样变成 I/O 计划

值层主线已经闭合：RowSet 进入 decoder，过滤结果返回 Vector。现在沿 PageReader 持有的 SeekableInputStream 追踪字节来源。一个 ColumnChunk 的 stream 不一定独占一次读取：同一 RowGroup 中不同列的 Regions 会先汇集到 BufferedInput，再按距离、大小和历史访问率规划。

先限定这里的 I/O 路径。默认 std::unique_ptr<dwio::common::BufferedInput> createBufferedInput( 在 ConnectorQueryCtx 提供 cache 时创建 CachedBufferedInput；没有 cache 的 Parquet 路径创建 DirectBufferedInput。Local Cache 属于前一分支，可结合 AsyncDataCache 与配置的 SSD cache 使用；它不是每一个 Parquet reader 都自带的缓存。下面具体分析 Direct 分支，不能把其中每次 ReadFile 读取描述成一次缓存查找。

16.1 enqueue 注册，load 规划

DirectBufferedInput::enqueue 创建 DirectInputStream，记录 Region、TrackingId 和 stream 指针，返回流对象而不立即读取。zero-length region 返回空数组流；whole-file preload 情况直接复用 preload data，通常不再登记 coalesced request。开始新一轮 enqueue 时，旧 coalescedLoads 和 stream-to-load 映射会清理，旧结果不能被当成永久索引。

16.2 两个预算决定“合并到多大”

maxCoalesceDistance 控制相邻请求允许跨过多远的 gap。prefetch 类采用 maxCoalesceBytes 追求较大的吞吐读取；sparse 类采用 loadQuantum 限制过读。单个 request 计入分组的大小还可能按 quantum 截断，不是简单把 region.length 直接求和后画一个大矩形。图中的 A+B 只是在距离与字节预算都满足时的算例。

17. DirectCoalescedLoad：分配、共享与成功发布

I/O 计划还需要落实到内存：一组 request 的数据是分别分配、共同分配，还是适合用小字节数组？这里的目标不只是降低 malloc 次数，还包括避免每个小 region 各自按页取整导致的浪费，同时保证 DirectInputStream 拿到的数据在使用期间有效。

DirectCoalescedLoad 表示一个合并加载任务，最终调用 ReadFile::read(ranges, offset)。ranges 可跨 MemoryPool 的多个连续 runs，也可包含 gap 占位；一次这层调用不保证等于一次操作系统 read，更不等于一次本地磁盘寻址。具体 ReadFile 可由远程存储等后端实现。

17.1 tiny、owned pages 与 shared allocation

computeLoadSizes 确定各 request 实际 requestBytes，普通大 request 分配页时会发生 page-rounding。shared allocation 受配置开关和累计过度分配是否超过最小 allocation run 的阈值影响；不能简单写成“大 request 一律 shared”。尾部 request 常按 loadQuantum 截断，位于合并组中间且要连接后续请求的 region 则可能一次完整读取，并检查 int32_t 容量上界。

  • tinyData：小请求使用连续字节数组；数据被移交给对应 stream。
  • ownedData：MemoryPool 分配非连续 pages；getData 转移 Allocation，Next 按其中连续 run 暴露数据。
  • sharedData：slice 属于 load 内的共享 allocation；stream 保存 sharedPtr，并用 sharedHolder 持有 load，维持 slice 生命周期。

完全相同 offset/length 的 duplicate request 不重复生成底层读取。shared 路径下消费者可以共用同一只读 slice；非 shared 路径为不同消费者准备副本。getData 对已移交的 buffer 标记 consumed，避免再次移动同一 buffer；shared slice 则无需移动。这比“stream 只是一个指针，不拥有数据”复杂得多。

        return request.region.offset < targetOffset;
      });

    // nothing is moved.
    return LoadedBuffer{

        .sharedData = it->buffer.sharedData,
    };
  }

         it->bufferConsumed) {

  }

  }

  std::unique_ptr<folly::SharedPromise<bool>> promise;
  {
    std::lock_guard<std::mutex> l(mutex_);
    state_ = endState;
    promise.swap(promise_);
  }
  if (promise != nullptr) {
    promise->setValue(true);
  }
}

loadData 抛 std::exception 时，执行线程把状态改成 kCancelled，再重抛异常。setEndState 将 SharedPromise 移出 mutex 保护范围后 setValue(true)，成功与取消都会唤醒等待者；这里没有 setException。因此 wait 的意义是“先前的加载结束了”，不是“读取成功”或“收到原始 I/O 异常”。

等待者随后 getData 看到非 Loaded 得到空 buffer，DirectInputStream 会落到 loadSync，重新在消费路径读取；若该读取也失败，异常在当前查询调用栈中出现。预取任务本身的异常还受 executor 的任务执行方式影响，不能声称当前 SharedPromise 自动把后台异常传递给所有 query waiters。读取到的部分 buffer 始终受 getData 的状态检查保护。

reset 会 cancel 当前 loads，并清空 requests 与映射。这里的 cancel 调用 setEndState(kCancelled) 并通知等待者，不会抢占底层 ReadFile 的进行中调用。setEndState 也没有校验旧状态；如果 cancel 与已经执行的 loadData 交错，后者完成时仍可再写入 kLoaded。因此图中描述的是一次 load 的正常成功/异常路径，不能把 kCancelled 理解成对所有并发交错都不可退出的终态。后台闭包的 AsyncLoadHolder 保持 load 和 MemoryPool 引用，也是保证异步任务运行时对象有效的组成部分。

与此处不同，TableScan 的 split preload 使用 AsyncSource。AsyncSource 会保存 exception_ptr，并在消费者 move() 时 rethrow；DirectCoalescedLoad 的 SharedPromise 则仅作结束通知。这两种异常通道不能因为都出现 future 就合并为同一套机制。下一节把 split 层的所有权与接管过程单独列出。

19. Split preload、接管与 reader 的生命周期

TableScan::checkPreload 在配置允许、connector 支持且有 ioExecutor 时安装 split preloader。preload 创建 AsyncSource<DataSource>，捕获 output type、table handle、columns、connector、独立 ConnectorQueryCtx、Task 和 split；executor 调用 prepare，实际工作仍是 createDataSource + addSplit。它预制的是一个准备好的 DataSource，不只是预先读取一个裸 buffer。

19.1 AsyncSource 如何把准备失败交给消费方

AsyncSource 的 mutex 保护 Init/Making/Prepared/Failed 等状态。prepare 取得 itemMaker 后在锁外执行；move 如果先到且仍是 Init，可以自己完成准备，如果已经 Making 则等待。如果 itemMaker 失败，makeItem 保存异常并通知等待者，move 检查 exception_ 后重新抛出。与 CoalescedLoad 的结束通知相比，AsyncSource 明确承担“把制作结果或原始异常交给消费者”的职责。

后台闭包捕获 Task 的 shared_ptr，是为了在准备可能晚于调度活动结束时保持所需 memory pools 存活，并在开始及关键阶段检查任务是否取消。取消不能理解为抢占底层已经开始的 ReadFile 调用。getSplit 取得 preparedDataSource 为空时检查 Task cancellation；其余错误仍应进入查询错误处理，而不是被当成一个空 split。

21. 从 Spark、native reader 与 Photon 看接口边界

读完 Velox 的完整路径，再回看行业方案，比较点就更具体：谁产生 selection，selection 能传到哪一层，payload 什么时候物化，JVM 与 native 之间如何交换向量。下面保留原分享的 Spark / native reader / Photon 背景，但将公开接口与 Velox 的具体实现分开。

Velox 原生 Parquet reader 沿用了 DWRF selective reader 的许多抽象：ScanSpec 表达读取要求，ColumnReader 接受 RowSet，ColumnVisitor 融合过滤与提取，VectorLoader 把计算层的访问需求带回读取层。原分享提及早期 DuckDB 路径的性能差距；没有同一数据、查询和版本的基准，不能把“只有 DWRF 的 50%”当作当前通用结论。原生 reader 的设计动机和社区讨论可见文末资料。

Spark 社区的 LazyColumnVector 提案把一个问题提得很直接：如果 payload 未被访问，就不应先物化它。但实现不能停在 ColumnVector 的 wrapper：vectorized reader 要改变列访问次序，selection 要到达 parquet-mr 的 decoder，嵌套类型和 dictionary page 也要理解同一组行坐标。图中的“过滤在前”意味着先读 predicate 列并求值，不是在没有读取 predicate 数据时凭空执行过滤。

DBR/native reader 的公开材料展示了另一种组织方式：JVM vectorized reader 请求各列，native reader 接收堆外状态与 vector 指针，解码 predicate 列并生成 mask，再据此减少 payload 解码。Photon 使用原生向量化执行，但具体的预取、缓存和 page 选择策略应以公开材料为界，不能由示意图推断其闭源实现与 Velox 相同。原分享中有关作者去向和提案未完成原因的个人归因，不作为技术结论。

在原分享所引用的 Photon 计划图中，JVM 侧的 FileScan 经 Adapter 进入 PhotonFilter、PhotonShuffle，随后通过 Transition 回到 JVM 的 ToObject。它展示的是原生执行片段如何接入已有计划，而不是声称整条链中的每个节点都被替换。native reader 的堆外 state、data/dictionary IDs 和 nulls vectors 又是更低一层的数据接口：Generated code 请求 batch 后，仍需要能够正确解释这些布局和有效行 mask。

Velox 把 selection 分成 reader 内和表达式层两段：SubfieldFilter 可以在单个字段的读取过程中判断；remaining filter 由 ExprSet 求值；两段得到的选择结果都可能继续减少 payload 的解码。后文将具体追踪它们之间的坐标转换。

22. 设计取舍：选择信息如何跨越计算与存储边界

这些实现面对的不是一个单独的“更快解码”问题，而是多个约束的协调：过滤条件直到运行时才知道，文件以压缩页组织，下游可能只访问一部分值，I/O 又希望用较大的请求隐藏延迟。设计的价值应从它如何化解这些矛盾来评估。

22.1 把行集合做成接口，跨过解码与计算边界

RowSet 很窄，却足以连接多个优化：过滤列只需交出通过行号，后续 reader 不必理解上一个 filter 的具体表达式；Lazy loader 只需把输出 indices 映射回父 reader 的 rows，就能把计算层的筛选带回 Parquet decoder。好处是模块职责清晰，代价是每一层必须维护一致的坐标、null 和生命周期。

22.2 两阶段给自适应读取顺序留出空间

若每读一列就立即固定最终输出，后续 filter 每次继续丢行，都要回头改已经产出的 vectors。read/getValues 分开后，过滤顺序可以变化，先读值只在最终 RowSet 确定后 compact，payload 还能继续 lazy。代价是 reader 需要暂存 values、outputRows 和 nulls，不能把解码对象看成无状态函数。

22.3 公共抽象与模板专用路径并存

格式无关类把 projection、filter、null、RowSet 和 Vector 组装共用起来；格式实现处理 encoding、page 和 levels。模板把 filter kind、值宽度与 dense 情形变成具体实例，减少热循环分支。代价是调用链更深、编译实例更多，阅读时容易把通用基类支持的能力误判为每种格式都支持。本文特别区分 Parquet 与 Nimble 的 lazy I/O 就是这个边界。

22.4 自适应预取不等于全局最优

ScanTracker 根据历史访问率避免总是预取所有 payload，coalescing 用少量 overread 换取更少的请求和更好的吞吐。但过滤相关性、数据分布变化以及不同列的访问热点会让历史失真。ScanSpec 的 timeToDropValue 同样只反映局部过滤代价。正确的工程做法是保留可观测统计和退路，而不是宣称一个 heuristic 在所有查询上都优于其他顺序。

这套 reader 最有价值的地方，是让“先筛哪些行、何时读哪些列、从哪里取得哪些字节、何时交付哪些 buffer”可以分别优化，又通过明确的 RowSet 和生命周期约束接起来。也正因为这些约束存在，解释性能必须落到具体路径，不能只列 LazyVector、SIMD、prefetch 等功能名。

22.5 把文件变化留在 split 边界，把查询意图保留在 ScanSpec

分区值、缺失字段、bucket conversion 都随文件变化；输出 schema 和过滤目标则属于查询。Hive/File 的分层让两类信息在 addSplit 时汇合，Reader/RowReader 的分层又把文件元数据和扫描游标分开。代价是继承链中出现多个 prepareSplit、两份 output type 和可移动的预制状态。理解时应沿真实调用点确认职责，不能仅凭相似类名推断。

22.6 延迟值物化和积极 I/O 可以同时存在

压缩页与远程请求有固定成本；完全按最终行号发细粒度请求往往得不偿失。Velox 允许字节先预取、值后解码，再用访问历史抑制长期不用的 stream。收益是吞吐和计算节省可以独立获得，代价是预取内存、gap 过读和命中预测误差。LazyVector 的价值首先是避免不需要的 values 与下游工作，额外节省多少存储 I/O 需要由实际路径证明。

把具体输入走完后，可以看到三个独立但相关的优化目标：减少候选行、减少值的解码或物化、减少存储字节。它们分别由过滤与 RowSet、read/getValues 与 LazyVector、BufferedInput 与 cache/preload 控制。评估时保留三层计数，才能判断一个改动只是把工作推迟，还是确实减少了总工作；异常和 reader 生命周期则是这些优化成立之前必须满足的条件。

23.1 A. rowsForPage：page 切片与输入坐标

源码摘录 · PageReader.cpp:1163

bool PageReader::rowsForPage(
    dwio::common::SelectiveColumnReader& reader,
    bool hasFilter,
    bool mayProduceNulls,
    folly::Range<const vector_size_t*>& rows,
    const uint64_t* FOLLY_NULLABLE& nulls) {
  if (currentVisitorRow_ == numVisitorRows_) {
    return false;
  }
  int32_t numToVisit;
  // Check if the first row to go to is in the current page. If not, seek to the
  // page that contains the row.
  auto rowZero = visitBase_ + visitorRows_[currentVisitorRow_];
  if (rowZero >= rowOfPage_ + numRowsInPage_) {
    seekToPage(rowZero);
    // If seekToPage set numRowsInPage_=0, we've reached the end of the chunk
    if (numRowsInPage_ == 0) {
      return false;
    }
    if (hasChunkRepDefs_) {
      numLeafNullsConsumed_ = rowOfPage_;
    }
  }
  auto& scanState = reader.scanState();
  if (isDictionary()) {
    if (scanState.dictionary.values != dictionary_.values) {
      scanState.dictionary = dictionary_;
      if (hasFilter) {
        makeFilterCache(scanState);
      }
      scanState.updateRawState();
    }
  } else {
    if (scanState.dictionary.values) {
      // If there are previous pages in the current read, nulls read
      // from them are in 'nullConcatenation_' Put this into the
      // reader for the time of dedictionarizing so we don't read
      // undefined dictionary indices.
      if (mayProduceNulls && reader.numValues()) {
        reader.setNulls(nullConcatenation_.buffer());
      }
      reader.dedictionarize();
      // The nulls across all pages are in nullConcatenation_. Clear
      // the nulls and let the prepareNulls below reserve nulls for
      // the new page.
      reader.setNulls(nullptr);
      scanState.dictionary.clear();
    }
  }

  // Then check how many of the rows to visit are on the same page as the
  // current one.
  int32_t firstOnNextPage = rowOfPage_ + numRowsInPage_ - visitBase_;
  if (firstOnNextPage > visitorRows_[numVisitorRows_ - 1]) {
    // All the remaining rows are on this page.
    numToVisit = numVisitorRows_ - currentVisitorRow_;
  } else {
    // Find the last row in the rows to visit that is on this page.
    auto rangeLeft = folly::Range<const int32_t*>(
        visitorRows_ + currentVisitorRow_,
        numVisitorRows_ - currentVisitorRow_);
    auto it =
        std::lower_bound(rangeLeft.begin(), rangeLeft.end(), firstOnNextPage);
    assert(it != rangeLeft.end());
    assert(it != rangeLeft.begin());
    numToVisit = it - (visitorRows_ + currentVisitorRow_);
  }
  // If the page did not change and this is the first call, we can return a view
  // on the original visitor rows.
  if (rowOfPage_ == initialRowOfPage_ && currentVisitorRow_ == 0) {
    nulls =
        readNulls(visitorRows_[numToVisit - 1] + 1, reader.nullsInReadRange());
    rowNumberBias_ = 0;
    rows = folly::Range<const vector_size_t*>(visitorRows_, numToVisit);
  } else {
    // We scale row numbers to be relative to first on this page.
    auto pageOffset = rowOfPage_ - visitBase_;
    rowNumberBias_ = visitorRows_[currentVisitorRow_];
    skip(rowNumberBias_ - pageOffset);
    // The decoder is positioned at 'visitorRows_[currentVisitorRow_']'
    // We copy the rows to visit with a bias, so that the first to visit has
    // offset 0.
    rowsCopy_->resize(numToVisit);
    auto copy = rowsCopy_->data();
    // Subtract 'rowNumberBias_' from the rows to visit on this page.
    // 'copy' has a writable tail of SIMD width, so no special case for end of
    // loop.
    for (auto i = 0; i < numToVisit; i += xsimd::batch<int32_t>::size) {
      auto numbers = xsimd::batch<int32_t>::load_unaligned(
                         &visitorRows_[i + currentVisitorRow_]) -
          rowNumberBias_;
      numbers.store_unaligned(copy);
      copy += xsimd::batch<int32_t>::size;
    }
    nulls = readNulls(rowsCopy_->back() + 1, reader.nullsInReadRange());
    rows = folly::Range<const vector_size_t*>(
        rowsCopy_->data(), rowsCopy_->size());
  }
  reader.prepareNulls(rows, nulls != nullptr, currentVisitorRow_);
  currentVisitorRow_ += numToVisit;
  firstUnvisited_ = visitBase_ + visitorRows_[currentVisitorRow_ - 1] + 1;
  return true;
}

      !(hasFilter && hasHook), "hasFilter and hasHook cannot both be true");

  bool mayProduceNulls = !filterOnly && visitor.allowNulls();
  auto rows = visitor.rows();
  auto numRows = visitor.numRows();
  auto& reader = visitor.reader();
  startVisit(folly::Range<const vector_size_t*>(rows, numRows));
  rowsCopy_ = &visitor.rowsCopy();
  folly::Range<const vector_size_t*> pageRows;
  int32_t numPageRowsRead = 0;
  const uint64_t* nulls = nullptr;
  bool isMultiPage = false;
  while (rowsForPage(reader, hasFilter, mayProduceNulls, pageRows, nulls)) {
    bool nullsFromFastPath = false;
    const int32_t numValuesBeforePage =
        numValuesRead<hasFilter, hasHook>(reader, numPageRowsRead);
    visitor.setNumValuesBias(numValuesBeforePage);
    visitor.setRows(pageRows);
    callDecoder(nulls, nullsFromFastPath, visitor);
    if (encoding_ == thrift::Encoding::DELTA_BINARY_PACKED &&
        deltaBpDecoder_->validValuesCount() == 0) {
      VELOX_DCHECK(
          deltaBpDecoder_->bufferStart() == pageData_ + encodedDataSize_,
          "Once all data in the delta binary packed decoder has been read, "
          "its buffer ptr should be moved to the end of the page.");
    }
    if (currentVisitorRow_ < numVisitorRows_ || isMultiPage) {
      if (mayProduceNulls) {
        if (!isMultiPage) {
          // Do not reuse nulls concatenation buffer if previous
          // results are hanging on to it.
          if (multiPageNulls_ && !multiPageNulls_->unique()) {
            multiPageNulls_ = nullptr;
          }
          nullConcatenation_.reset(multiPageNulls_);
        }
        if (!nulls) {
          nullConcatenation_.appendOnes(
              numValuesRead<hasFilter, hasHook>(reader, numPageRowsRead) -
              numValuesBeforePage);
        } else if (reader.returnReaderNulls()) {
          // Nulls from decoding go directly to result.
          nullConcatenation_.append(
              reader.nullsInReadRange()->template as<uint64_t>(),
              0,
              numValuesRead<hasFilter, hasHook>(reader, numPageRowsRead) -
                  numValuesBeforePage);
        } else {
          // Add the nulls produced from the decoder to the result.
          auto firstNullIndex = nullsFromFastPath ? 0 : numValuesBeforePage;
          nullConcatenation_.append(
              reader.mutableNulls(0),
              firstNullIndex,
              firstNullIndex +
                  numValuesRead<hasFilter, hasHook>(reader, numPageRowsRead) -
                  numValuesBeforePage);
        }
      }
      isMultiPage = true;
    }
    // The passing rows on non-first pages are relative to the start
    // of the page, adjust them to be relative to start of this
    // read. This can happen on the first processed page as well if
    // the first page of scan did not contain any of the rows to
    // visit.
    if (hasFilter && rowNumberBias_) {
      reader.offsetOutputRows(numValuesBeforePage, rowNumberBias_);
    }
    numPageRowsRead += pageRows.size();
  }
  if (isMultiPage) {
    reader.setNulls(mayProduceNulls ? nullConcatenation_.buffer() : nullptr);
  }
}

建议按这条链阅读：FileDataSource::next → ParquetRowReader::next → StructColumnReader::read → SelectiveStructColumnReaderBase::read → leaf reader / ColumnVisitor → PageReader；再回到 getValues → ExprSet → ColumnLoader，最后沿 DirectInputStream 查到 BufferedInput 和 CoalescedLoad。每次进入下一层，都先确认输入 rows 的坐标和对象生命周期。
