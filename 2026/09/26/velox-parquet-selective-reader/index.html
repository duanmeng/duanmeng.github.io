Velox Parquet SelectiveReader：过滤下推、延迟物化与 I/O 调度

duanmeng
2026-09-26
technology
IO, Parquet, PredicatePushdown, SelectiveReader, Velox

Velox Parquet SelectiveReader 是 Velox 的原生 Parquet 列式读取实现。它在扫描过程中执行能够下推的过滤条件，把通过的行号集合交给后续列，并把不急于使用的列延迟到真正访问时再解码。读取结果是一个带 Velox schema 的 RowVector；其中有已经物化的 child，也可以有仍由 loader 管理的 LazyVector。

例如查询 SELECT name, comment FROM nation WHERE nationkey BETWEEN 0 AND 3 AND regionkey = 0：reader 先读 nationkey，用通过的行号去读 regionkey；只有两个条件都通过的行，才需要 name 和 comment。整个文件并不因此变成“每行单独读取”：RowGroup、压缩页、预取和合并 I/O 各自有物理边界。SelectiveReader 要协调的，就是逻辑上只要这些行，物理上怎样尽量少做工作。

下面从一次 TableScan 读取讲起，先建立 Reader、ColumnReader、PageReader 与 Vector 的关系，再用 nation 和嵌套 contacts 两个例子展开过滤、解码与物化，最后讨论 I/O 的线程、内存所有权和设计取舍。涉及的函数均以固定源码版本为准；源码摘录可通过链接定位，SQL、schema 和状态算例单独标注。

源码基准：Velox 235512ebfb44（2026-09-26 origin/main）。本文在原 SelectiveReader 分享基础上保留并展开数据例子、调用链和 PageReader 附录。文内代码是阅读源码用的摘录，未作为独立程序编译。

1. 一次 TableScan 读取经过哪些对象

Driver 持有一串 Operator 实例，在 executor 的工作线程上推进它们。TableScan 是 pipeline 的数据源，通过 Connector 的 DataSource 获取 batch。Driver 不是永久绑定线程的对象；遇到算子级 blocked future 时可以 off-thread，future 满足后再排队。这个调度协议与后文 DirectInputStream 在调用栈里同步等待 I/O 是两件不同的事。

1.1 收到 split：准备文件与查询需要的 schema

Hive split 描述文件路径、字节范围以及分区值等信息。当前公共逻辑在 FileDataSource / FileSplitReader，HiveDataSource / HiveSplitReader 在此基础上处理 Hive 特有内容。FileDataSource 收到 split 后创建 split reader，配置 options，然后调用 prepareSplit。

1.3 扫描推进与输出数量必须分清

ParquetRowReader::next(size, output) 的返回值是扫描位置推进的行数；output->size() 是 reader filters 之后的输出行数。扫描 11 行只留下 1 行时，二者分别是 11 和 1。扫描非零而输出为空也正常，表示这个 batch 全被过滤；返回扫描数为零才是这一读取路径的结束信号。FileDataSource 还可能再应用 remaining filter，使最终返回的 RowVector 更小。

2. 延迟物化需要哪些接口配合

Velox 原生 Parquet reader 沿用了 DWRF selective reader 的许多抽象：ScanSpec 表达读取要求，ColumnReader 接受 RowSet，ColumnVisitor 融合过滤与提取，VectorLoader 把计算层的访问需求带回读取层。原分享提及早期 DuckDB 路径的性能差距；没有同一数据、查询和版本的基准，不能把“只有 DWRF 的 50%”当作当前通用结论。原生 reader 的设计动机和社区讨论可见文末资料。

Spark 社区的 LazyColumnVector 提案把一个问题提得很直接：如果 payload 未被访问，就不应先物化它。但实现不能停在 ColumnVector 的 wrapper：vectorized reader 要改变列访问次序，selection 要到达 parquet-mr 的 decoder，嵌套类型和 dictionary page 也要理解同一组行坐标。图中的“过滤在前”意味着先读 predicate 列并求值，不是在没有读取 predicate 数据时凭空执行过滤。

DBR/native reader 的公开材料展示了另一种组织方式：JVM vectorized reader 请求各列，native reader 接收堆外状态与 vector 指针，解码 predicate 列并生成 mask，再据此减少 payload 解码。Photon 使用原生向量化执行，但具体的预取、缓存和 page 选择策略应以公开材料为界，不能由示意图推断其闭源实现与 Velox 相同。原分享中有关作者去向和提案未完成原因的个人归因，不作为技术结论。

在原分享所引用的 Photon 计划图中，JVM 侧的 FileScan 经 Adapter 进入 PhotonFilter、PhotonShuffle，随后通过 Transition 回到 JVM 的 ToObject。它展示的是原生执行片段如何接入已有计划，而不是声称整条链中的每个节点都被替换。native reader 的堆外 state、data/dictionary IDs 和 nulls vectors 又是更低一层的数据接口：Generated code 请求 batch 后，仍需要能够正确解释这些布局和有效行 mask。

Velox 把 selection 分成 reader 内和表达式层两段：SubfieldFilter 可以在单个字段的读取过程中判断；remaining filter 由 ExprSet 求值；两段得到的选择结果都可能继续减少 payload 的解码。后文将具体追踪它们之间的坐标转换。

3. Parquet 物理布局决定了裁剪的边界

3.1 RowGroup、ColumnChunk 与 footer

Parquet 可以看作文件级的 PAX 风格组织：先按行水平切成 RowGroup，再把每个 RowGroup 内各叶子列的数据分别放进 ColumnChunk。一个包含 A、B、C 三个叶子列和两个 RowGroup 的文件，共有六个 ColumnChunk。每个 chunk 有一个或多个 page；字典编码时可能先有 dictionary page。不同列的 page 大小和行边界不要求对齐。

footer 保存 schema、RowGroup 行数、ColumnChunk 位置与长度、codec、encoding、统计等元数据。reader 可以在解码数据前用这些信息选择范围。简单文件还在首尾使用 PAR1 标识，尾部记录 footer 长度；图中聚焦 chunk 与 footer，并未按真实字节比例画所有格式字段。

3.2 Data Page V1 与 V2 的压缩边界

逻辑布局示意；不是 C++ 数据结构

[ PageHeader: Thrift, variable length ]
[ repetition levels, if present ]
[ definition levels, if present ]
[ encoded values ]

V1 在启用 codec 时，对页体中的 levels 与 encoded values 整体压缩。V2 在 header 中给出 repetition_levels_byte_length 和 definition_levels_byte_length，levels 本身不压缩；values 是否压缩由 is_compressed 决定。当前 prepareDataPageV2() 把缺省 is_compressed 按 true 处理，并验证 levelsSize 不超过 compressed/uncompressed page size。分析读取成本时，需要按 page version 分开计算 levels 与 values 的处理。

“page 内只需要两行”通常无法让通用压缩器只解压两行对应的字节。reader 需要先获得对应压缩块，再在 encoded values 中跳过不需要的项。不过，value decode、结果写入以及后面列的读取仍可以少做。这正是 page 裁剪与 row 裁剪应该分别讨论的原因。

4. repetition / definition levels 怎样描述嵌套数据

4.1 层级来自 schema path

保留原分享的 AddressBook 示例。这里 contacts 是 repeated group，因此逻辑上是 ARRAY(ROW(name VARCHAR, blockID BIGINT))，而非单个 struct。每条 leaf column 保存沿自身路径的 levels 和实际值：owner、contacts.name、contacts.blockID。

4.3 现代 LIST 为什么不能复用同一组 DL 数字

对比 schema：明确列出 nullable list 和 nullable element

optional group contacts (LIST) {
  repeated group list {
    optional group element {
      required binary name (UTF8);
      optional int64 blockID;
    }
  }
}

在这份现代 LIST 示例中，到 name 的 maxDL=3，到 blockID 的 maxDL=4，maxRL 仍是 1。DL=0 可以表达 null list，DL=1 表达 empty list，DL=2 表达 null element；再往下才是 element 内的字段状态。换一份 element required 的 schema，数值又会变化。2026-09-26 基准中的 legacy nested schema 修正涉及 maxDefine 传播，说明 reader 必须按真实路径计算，不能从 SQL ARRAY 类型直接猜 levels。

5. Type、Vector、ColumnReader 各自是一棵什么树

文件 schema、查询 requested type、运行时 Vector 和 reader tree 有关联，但不是同一个对象。requested type 使用 Velox Type 描述逻辑语义；ParquetTypeWithId 还保留物理 schema、列号、父子路径和 level 信息；Vector 表示输出数据和编码；ColumnReader 维护解码与扫描状态。

以 ROW(c0 BIGINT, c1 MAP(VARCHAR, DOUBLE)) 为例，顶层 RowVector 直接有两个 child：c0 的整数 vector 和 c1 的 MapVector。MapVector 自己有 offsets、sizes 和 nulls，再持有 key/value vectors。因此总共三条 leaf values 流，但绝不能说整棵树只有三个 Vector。reader 一侧对应 root StructColumnReader、IntegerColumnReader、MapColumnReader，map 下再有 StringColumnReader 与 FloatingPointColumnReader<double,double>。

工厂 ParquetColumnReader::build 根据 fileType 的 Velox kind 选择具体 reader，再结合 requestedType 处理读取结果类型。整数走 IntegerColumnReader；REAL 可按 requested type 输出 float 或 double；ARRAY/MAP/ROW 走相应复杂 reader；timestamp 还要区分文件 INT64/INT96。C++ 值类型由 decoder/visitor 模板承接，和顶层 logical Type 的职责不同。

StructColumnReader 构造时使用 ScanSpec::stableChildren() 建立 children_，为每个真实 reader 设置 subscript。之后 ScanSpec::children() 可以因过滤重排而改变顺序；reader 在 children_ 中的位置和输出 channel 都不能跟着随意变。channel 指输出列位置，subscript 指实际 reader 位置，遍历顺序指当前读取优先级，必须分清。

复杂节点并不总有自己的物理值 stream。嵌套 struct 的 nullability 需要从 descendant leaf 的 RL/DL 推导；本版本还有 synthetic rep/def source：当逻辑投影 child 不足以提供结构信息时，选择一个物理叶子专门读取 levels。源码按完整 metadata、读取字节、解压字节、numValues 等成本选择候选。因此 reader tree 与“查询投影的物理叶子”也不是无条件一一对应。

6. ScanSpec 与过滤重排：先读哪一列

6.1 一个节点同时描述查询意图和运行时反馈

ScanSpec 信息读取时的用途
fieldName / children按名字找到文件字段，递归处理复杂类型
projectOut / channel是否输出、放入输出 RowVector 的哪一列
constantValue / columnType分区值、缺失字段、row index 或合成列

hasFilter() 不是简单检查 filter_ 非空。一个 struct 的自身 filter_ 可能为空，但其 child 有 filter，仍会影响 parent 的行数。array element/map key 的子筛选又未必改变容器输出行数，ScanSpec 对这类路径有专门判断。把它概括成“scalar 总比 complex 优先”会丢失这些语义。

6.2 用丢掉一行的代价排序，而不是只看选择率

  float timeToDropValue() const {
    if (numIn_ == numOut_) {
      return timeClocks_;
    }
    return timeClocks_ / static_cast<float>(numIn_ - numOut_);

假设 filter A 花 1000 clocks 丢 900 行，约 1.11 clocks/drop；filter B 花 100 clocks 丢 10 行，是 10 clocks/drop。B 单次总耗时较低，但 A 更适合提前缩小后续输入。没有丢行时，当前实现返回累计 timeClocks_，并不是除以零或返回无限大。这个指标是局部自适应启发式，不是完整代价优化器，也不显式建模后续列压缩比和远程延迟。

    }
    // If hasFilter() is true but 'filter_' is nullptr, we have a filter
    // on complex type members. The simple type filter goes first.
    if (left->filter_) {
      return true;
    }
    if (right->filter_) {
      return false;
    }
    return left->fieldName_ < right->fieldName_;
  }

  if (left->hasFilter()) {
    return true;
  }
  if (right->hasFilter()) {
    return false;
  }
  return left->fieldName_ < right->fieldName_;
}

9. PageReader：page 边界、行号与 nulls 必须一起推进

9.1 RowSet 不是一个固定的文件绝对坐标

PageReader 中 visitorRows 是当前 visit 的相对行号，visitBase_ 由 startVisit 从 firstUnvisited_ 取得。对普通标量列，可以把两者之和理解为当前 ColumnChunk 对应的行位置；重复嵌套列的 leaf level/value 数不等于顶层 RowVector 行数，必须先经结构层转换。原附录把所有 visitorRows 直接叫“全局绝对行号”，会混淆层级。

rowsForPage 首先判断 visitor 是否已消费完；然后计算下一目标 rowZero。如果它超出当前 page，seekToPage 逐步解析 PageHeader 并移动流。遇到 numRowsInPage_==0 表示 chunk 末尾，函数返回 false。已知 page 行范围且目标在后面时，可 skip 该页数据；重复列可能先需要读 levels 才能知道边界，跳过不是无条件的。

9.2 一个具体的跨页坐标算例

设 visitBase=1000，visitorRows=[5,8,210,215]。Page A 覆盖 [1000,1200)，Page B 覆盖 [1200,1400)。page 切片把前两项交给 A，后两项交给 B。到了 B，pageOffset=1200−1000=200，rowNumberBias=210，先 skip(10)，让 decoder 位于绝对行 1210，再用 [0,5] 表示两个目标。filter 产生的输出行号加回 210 后，才恢复成本 batch 的 [210,215]。

还有一个完全不同的 numValuesBias：它表示之前 page 已经向 values buffer 写入了多少项，用来定位当前 page 结果的追加位置。输入行号的 bias 与输出 buffer 的 bias 不能互换。最后 firstUnvisited 更新为最后一个目标绝对位置加一，即本例 1216。

9.3 dictionary/direct 切换与 filter cache

同一 ColumnChunk 的 data pages 可以先 dictionary 后 plain。进入 dictionary page 时，scanState 指向当前字典，并在有 filter 时建立 filter cache。切到 direct page 前，如果先前积累的结果还是 dictionary ids，就要 dedictionarize。代码临时挂上已累计的 null bitmap，避免把 null 位置的未定义字典索引当作有效值读取；转换完成后清空 dictionary state，再准备新页 nulls。

9.4 多页 null bitmap 不能按输入长度盲目拼接

readWithVisitor 每页先记录 numValuesBeforePage，设置 visitor 的 rows 和 output bias，再 callDecoder。跨页时，BitConcatenation 按实际产出的值数拼接 nulls。没有 null 的页追加 ones（Velox 位图中 1 表示非空）；returnReaderNulls 的快路径直接取 reader 的输入 nulls；普通过滤/compact 路径取 mutableNulls，起点还要看 nullsFromFastPath 是否从零写入。

如果前一批输出仍共享 multiPageNulls_，代码先放弃复用旧 buffer，避免修改已交付的数据。delta binary packed decoder 耗尽时还校验内部指针到达页尾。最后把拼接结果 setNulls 回 reader，并用 rowNumberBias 修正通过行号。完整的两个函数保留在附录，正文逐一解释其状态。

10. Remaining filter 与 LazyVector：表达式怎样影响 payload 读取

10.1 单列 filter 和表达式层 filter 的边界

SubfieldFilter 是 reader 能识别的字段或 subfield 条件，例如整数范围、字符串范围、null 检查等。复杂函数、不能提取成这些条件的单列表达式，或 c0+c1>10 这样的多列计算，交给 remaining ExprSet。并不是“单列一定下推，多列一定不下推”：FileDataSource 先调用 extractFiltersFromRemainingFilter，把能提取的部分放回 filters_，其余才编译为表达式。

payload 是不参与当前 predicate 的投影列。LazyVector 是带逻辑长度和 VectorLoader 的延迟表示，不保证文件 I/O 尚未发生：可能已经 prefetch 了压缩数据，只是尚未 decode 成 values。区分“延迟 stream I/O”和“延迟 value materialization”十分关键。

10.2 Parquet 的真实 lazy 条件，不由 remainingFilterColumns 直接决定

FileDataSource 确实收集 remainingFilterColumns_ 并传到 RowReaderOptions，但在本文版本中，直接使用 remainingFilterColumns() 排除 lazy I/O 列的是 SelectiveNimbleRowReader::computeLazyIoColumns()。它控制 Nimble 的 stream I/O 延迟集合，也不等于所有格式的统一 eager-vector 开关。Parquet 的 StructColumnReader 没有消费这个集合；其 lazy 条件是第 7 章源码中的 top-level/projectOut/filter/generateLazyChildren。

因此，Parquet reader 返回时，remaining filter 引用的列仍可能是 LazyVector。ExprSet 求值会加载实际需要的字段；对多次引用或 shouldEagerlyMaterialize 判断出的字段，FileDataSource 在 evaluateRemainingFilter 前显式 ensureLoadedRows，避免同一个 lazy child 在多个表达式分支中被不一致地局部加载。过滤需要但 SQL 不投影的字段会补进 readerOutputType，求值后再去掉。

void DirectBufferedInput::load(const LogType /*unused*/) {
  // After load, new requests cannot be merged into pre-load ones.
  auto requests = std::move(requests_);
  std::vector<LoadRequest*> storageLoad[2];
  for (auto& request : requests) {
    cache::TrackingData trackingData;
    const bool prefetchAnyway = request.trackingId.empty() ||
        request.trackingId.id() == StreamIdentifier::sequentialFile().id_;
    if (!prefetchAnyway && tracker_) {
      trackingData = tracker_->trackingData(request.trackingId);
    }
    const int loadIndex =
        (prefetchAnyway || isPrefetchablePct(adjustedReadPct(trackingData)))
        ? 1
        : 0;
    storageLoad[loadIndex].push_back(&request);
  }
  std::sort(storageLoad[1].begin(), storageLoad[1].end(), lessThan);
  std::sort(storageLoad[0].begin(), storageLoad[0].end(), lessThan);
  std::vector<int32_t> groupEnds[2];
  groupEnds[1] = groupRequests(storageLoad[1], true);
  moveCoalesced(
      storageLoad[1],
      groupEnds[1],
      storageLoad[0],
      [](auto* request) { return request->region.offset; },
      [](auto* request) {
        return request->region.offset + request->region.length;
      });
  groupEnds[0] = groupRequests(storageLoad[0], false);
  readRegions(storageLoad[1], true, groupEnds[1]);
  readRegions(storageLoad[0], false, groupEnds[0]);
}

13. DirectCoalescedLoad：数据怎样持有和交付

DirectCoalescedLoad 表示一个合并加载任务，最终调用 ReadFile::read(ranges, offset)。ranges 可跨 MemoryPool 的多个连续 runs，也可包含 gap 占位；一次这层调用不保证等于一次操作系统 read，更不等于一次本地磁盘寻址。具体 ReadFile 可由远程存储等后端实现。

13.1 tiny、owned pages 与 shared allocation

computeLoadSizes 确定各 request 实际 requestBytes，普通大 request 分配页时会发生 page-rounding。shared allocation 受配置开关和累计过度分配是否超过最小 allocation run 的阈值影响；不能简单写成“大 request 一律 shared”。尾部 request 常按 loadQuantum 截断，位于合并组中间且要连接后续请求的 region 则可能一次完整读取，并检查 int32_t 容量上界。

  • tinyData：小请求使用连续字节数组；数据被移交给对应 stream。
  • ownedData：MemoryPool 分配非连续 pages；getData 转移 Allocation，Next 按其中连续 run 暴露数据。
  • sharedData：slice 属于 load 内的共享 allocation；stream 保存 sharedPtr，并用 sharedHolder 持有 load，维持 slice 生命周期。

完全相同 offset/length 的 duplicate request 不重复生成底层读取。shared 路径下消费者可以共用同一只读 slice；非 shared 路径为不同消费者准备副本。getData 对已移交的 buffer 标记 consumed，避免再次移动同一 buffer；shared slice 则无需移动。这比“stream 只是一个指针，不拥有数据”复杂得多。

        .sharedData = it->buffer.sharedData,
    };
  }

loadData 抛 std::exception 时，执行线程把状态改成 kCancelled，再重抛异常。setEndState 将 SharedPromise 移出 mutex 保护范围后 setValue(true)，成功与取消都会唤醒等待者；这里没有 setException。因此 wait 的意义是“先前的加载结束了”，不是“读取成功”或“收到原始 I/O 异常”。

16. 这套设计的收益与代价

16.1 把行集合做成接口，跨过解码与计算边界

RowSet 很窄，却足以连接多个优化：过滤列只需交出通过行号，后续 reader 不必理解上一个 filter 的具体表达式；Lazy loader 只需把输出 indices 映射回父 reader 的 rows，就能把计算层的筛选带回 Parquet decoder。好处是模块职责清晰，代价是每一层必须维护一致的坐标、null 和生命周期。

16.2 两阶段给自适应读取顺序留出空间

若每读一列就立即固定最终输出，后续 filter 每次继续丢行，都要回头改已经产出的 vectors。read/getValues 分开后，过滤顺序可以变化，先读值只在最终 RowSet 确定后 compact，payload 还能继续 lazy。代价是 reader 需要暂存 values、outputRows 和 nulls，不能把解码对象看成无状态函数。

16.3 公共抽象与模板专用路径并存

格式无关类把 projection、filter、null、RowSet 和 Vector 组装共用起来；格式实现处理 encoding、page 和 levels。模板把 filter kind、值宽度与 dense 情形变成具体实例，减少热循环分支。代价是调用链更深、编译实例更多，阅读时容易把通用基类支持的能力误判为每种格式都支持。本文特别区分 Parquet 与 Nimble 的 lazy I/O 就是这个边界。

16.4 自适应预取不等于全局最优

ScanTracker 根据历史访问率避免总是预取所有 payload，coalescing 用少量 overread 换取更少的请求和更好的吞吐。但过滤相关性、数据分布变化以及不同列的访问热点会让历史失真。ScanSpec 的 timeToDropValue 同样只反映局部过滤代价。正确的工程做法是保留可观测统计和退路，而不是宣称一个 heuristic 在所有查询上都优于其他顺序。

这套 reader 最有价值的地方，是让“先筛哪些行、何时读哪些列、从哪里取得哪些字节、何时交付哪些 buffer”可以分别优化，又通过明确的 RowSet 和生命周期约束接起来。也正因为这些约束存在，解释性能必须落到具体路径，不能只列 LazyVector、SIMD、prefetch 等功能名。

    auto copy = rowsCopy_->data();
    // Subtract 'rowNumberBias_' from the rows to visit on this page.
    // 'copy' has a writable tail of SIMD width, so no special case for end of
    // loop.
    for (auto i = 0; i < numToVisit; i += xsimd::batch<int32_t>::size) {
      auto numbers = xsimd::batch<int32_t>::load_unaligned(
                         &visitorRows_[i + currentVisitorRow_]) -
          rowNumberBias_;
      numbers.store_unaligned(copy);
      copy += xsimd::batch<int32_t>::size;
    }
    nulls = readNulls(rowsCopy_->back() + 1, reader.nullsInReadRange());
    rows = folly::Range<const vector_size_t*>(
        rowsCopy_->data(), rowsCopy_->size());
  }
  reader.prepareNulls(rows, nulls != nullptr, currentVisitorRow_);
  currentVisitorRow_ += numToVisit;
  firstUnvisited_ = visitBase_ + visitorRows_[currentVisitorRow_ - 1] + 1;
  return true;
}

template <typename Visitor>
void PageReader::readWithVisitor(Visitor& visitor) {
  constexpr bool hasFilter =
      !std::is_same_v<typename Visitor::FilterType, common::AlwaysTrue>;
  constexpr bool filterOnly =
      std::is_same_v<typename Visitor::Extract, dwio::common::DropValues>;
  constexpr bool hasHook = Visitor::kHasHook;
  static_assert(
      !(hasFilter && hasHook), "hasFilter and hasHook cannot both be true");

  bool mayProduceNulls = !filterOnly && visitor.allowNulls();
  auto rows = visitor.rows();
  auto numRows = visitor.numRows();
  auto& reader = visitor.reader();
  startVisit(folly::Range<const vector_size_t*>(rows, numRows));
  rowsCopy_ = &visitor.rowsCopy();
  folly::Range<const vector_size_t*> pageRows;
  int32_t numPageRowsRead = 0;
  const uint64_t* nulls = nullptr;
  bool isMultiPage = false;
  while (rowsForPage(reader, hasFilter, mayProduceNulls, pageRows, nulls)) {
    bool nullsFromFastPath = false;
    const int32_t numValuesBeforePage =
        numValuesRead<hasFilter, hasHook>(reader, numPageRowsRead);
    visitor.setNumValuesBias(numValuesBeforePage);
    visitor.setRows(pageRows);
    callDecoder(nulls, nullsFromFastPath, visitor);
    if (encoding_ == thrift::Encoding::DELTA_BINARY_PACKED &&
        deltaBpDecoder_->validValuesCount() == 0) {
      VELOX_DCHECK(
          deltaBpDecoder_->bufferStart() == pageData_ + encodedDataSize_,
          "Once all data in the delta binary packed decoder has been read, "
          "its buffer ptr should be moved to the end of the page.");
    }
    if (currentVisitorRow_ < numVisitorRows_ || isMultiPage) {
      if (mayProduceNulls) {
        if (!isMultiPage) {
          // Do not reuse nulls concatenation buffer if previous
          // results are hanging on to it.
          if (multiPageNulls_ && !multiPageNulls_->unique()) {
            multiPageNulls_ = nullptr;
          }
          nullConcatenation_.reset(multiPageNulls_);
        }
        if (!nulls) {
          nullConcatenation_.appendOnes(
              numValuesRead<hasFilter, hasHook>(reader, numPageRowsRead) -
              numValuesBeforePage);
        } else if (reader.returnReaderNulls()) {
          // Nulls from decoding go directly to result.
          nullConcatenation_.append(
              reader.nullsInReadRange()->template as<uint64_t>(),
              0,
              numValuesRead<hasFilter, hasHook>(reader, numPageRowsRead) -
                  numValuesBeforePage);
        } else {
          // Add the nulls produced from the decoder to the result.
          auto firstNullIndex = nullsFromFastPath ? 0 : numValuesBeforePage;
          nullConcatenation_.append(
              reader.mutableNulls(0),
              firstNullIndex,
              firstNullIndex +
                  numValuesRead<hasFilter, hasHook>(reader, numPageRowsRead) -
                  numValuesBeforePage);
        }
      }
      isMultiPage = true;
    }
    // The passing rows on non-first pages are relative to the start
    // of the page, adjust them to be relative to start of this
    // read. This can happen on the first processed page as well if
    // the first page of scan did not contain any of the rows to
    // visit.
    if (hasFilter && rowNumberBias_) {
      reader.offsetOutputRows(numValuesBeforePage, rowNumberBias_);
    }
    numPageRowsRead += pageRows.size();
  }
  if (isMultiPage) {
    reader.setNulls(mayProduceNulls ? nullConcatenation_.buffer() : nullptr);
  }
}
